# heldout-reasoning

The endpoint returns 504 for a fraction of requests, and only ever on the second attempt. First hypothesis, retries: the client retries after a 504, so a retry that hits an endpoint holding a lock could serialize the request into its own earlier twin. That hypothesis predicted duplicate work, so it was tested by counting ids rather than arguing, and the ids came out single: one charge per order, no duplicates. Second hypothesis, the load balancer's idle timeout being shorter than the upstream's, predicted that the 504 would arrive on a flat latency distribution near that timeout, which it did not — the failures clustered at 31s while the idle timeout is 60s. The measurement that finally separated the cases was an upstream access log joined on trace id, which showed the upstream responding in 1.4s and the 504 arriving 30s later from the API gateway. What lives at 30s is a per-request timeout on the gateway's route for that one upstream, which someone had set while debugging something else in March and which had never been reverted. The reasoning was not hard, only ordered, and the order was: prove the idempotency claim before touching the timeout, because the timeout hypothesis is cheap to test and expensive to guess at when money moves.

A container exits with code 137 and `lastState.terminated.reason` says OOMKilled, but the JVM's own logs report 210Mi live heap under a 300Mi maximum and there is no allocation failure anywhere. The naive reading is that something outside the heap ate the container, and that reading is usually right, but it is not a diagnosis, so the two candidate explanations were separated before anything was changed: direct buffers and native allocations on one side, page-cache and tmpfs accounting on the other. The first would show up in `smaps_rollup` as anonymous memory; the second would show up as file-backed memory that the working-set metric excludes, meaning the second cannot produce an OOMKill at all, which is the reason it was dropped in under a minute without any new instrumentation. Native memory tracking then showed 96Mi of Direct Buffer, matching a client configured with a 64Mi pool and a second client added in the same release that no one had sized, so the total request was 300 plus 64 plus 64 plus thread stacks against a 512Mi limit. The fix was arithmetic and the lesson was that the limit is not a JVM property, and the alert that should have existed pages on working set against limit rather than waiting for the kernel to make the decision.

Two dashboards both show the login endpoint at 320ms p95 and one of them is wrong, but the interesting part is the argument about which. Hypothesis: the client-side metric includes network and is therefore the higher of the two, so the server metric is the honest one. That reasoning is fine and irrelevant, because the observed numbers were the other way round, and a clean theory that predicts the wrong sign should be discarded rather than refined. What was left after discarding it was sampling: the client metric is computed from a head-based trace sampler, and head sampling drops the slow tail when the tail is rare, so the client-side number was biased low while the server-side histogram was complete and biased only by its bucket boundaries, which are coarse at exactly the latency of interest. Two different biases in opposite directions that happen to land on the same number is what made them look like agreement. The way out was not a third dashboard but a boundary: an SLO measured from the server histogram with buckets placed around the threshold the product cares about, and the trace-derived number demoted to a debugging aid, documented as biased rather than trusted.

A p95 that was 180ms is now 380ms and the change log contains only refactors. The fast answer is a slow dependency, and the fast answer is usually wrong, so the first act was arithmetic rather than investigation: if two calls of 190ms and 175ms overlap, the request costs about 190ms, and if they stop overlapping it costs about 365ms, which is the number that showed up. That is a lot of information from a subtraction, and it redirected the whole question from which dependency got slower to why independent work became sequential, because the dependency spans had not moved at all. The mechanism was an `await` moved into a loop during a readability refactor, invisible in review because the loop body was correct and the loop itself was the bug. The general rule that came out of the afternoon is that totals that grow while parts stay flat are shape bugs, not speed bugs, and that a sum-versus-max comparison in the write-up costs nothing and settles what an afternoon of flamegraphs only suggests.

The conversion-rate dashboard said the redesign lost 6 percent and the revenue dashboard said it gained 4 percent, and the meeting spent twenty minutes arguing about which dashboard was lying. Neither was. The reasoning that ended the argument was not statistical: it was a definition check, run by reading the two queries instead of the charts. The conversion metric counted a session that reached checkout, so the redesign — which moved checkout behind a faster, shorter funnel — converted more sessions and pushed the low-intent ones into a page that the revenue metric then attributed less revenue per session to, because the same order was now credited to a session with fewer pageviews in it. Both numbers were correct measurements of different quantities, and the 6 percent and the 4 percent were not in tension at all, only in the same sentence. What should have been established before the meeting, and was established after it, was which quantity the decision was about: the invariant that survives the redesign is revenue per *visitor*, which moved neither up nor down, and the whole argument had been about a denominator that changed under the experiment. The lasting habit was to read the query before debating the chart, and to refuse any A/B readout whose headline metric has a denominator the treatment can move.

The estimate was wrong and the reasoning was right, which is the annoying case. A capacity model said the nightly job fits in the window with 40 percent headroom; the job overran by two hours on the third night. The model was built on throughput per worker measured in staging, and the measurement was honest, so the error had to be in what the model held constant. Three things were held constant that should not have been: the per-worker rate degrades with worker count because the job contends on one table's write lock, the input size for that night was the month-end file rather than the daily one, and the window is not a fixed number because the environment's own backup moved into it in April. The error is not arithmetic, it is that a model built by scaling one measured point implicitly claims the curve is a line. The repair was to measure the curve — throughput against worker count on the month-end file — and to write the model's assumptions next to its conclusion so that the next person who finds a two-hour overrun can attack an assumption instead of reverse-engineering a spreadsheet.

A retry storm on the identity provider appeared after a client update and disappeared after another one, and the interesting reasoning was about what to measure while it was still happening. If the storm were a token-expiry misalignment, retries would cluster at the same instant across clients, which per-minute histograms confirmed. If it were retry amplification from a shared failure, the retry count per request would exceed one, which the client's own counters also confirmed, so both hypotheses were live at once, and they were not rivals: expiry alignment was the trigger and amplification was the amplifier, and the fix that shipped removed the alignment (jittered refresh) and bounded the amplification (a cap plus a circuit that opens on the dependency rather than on the call). The reasoning worth keeping is that two measurements agreeing does not mean two hypotheses agreeing, and that a system with a synchronized clock and an unbounded retry will produce a storm from any common-mode event, so the durable fix is to break the synchronization rather than to make the dependency perfect.

---

The question was asked in the wrong order. A rate-limiter change was proposed to stop brute-force attempts on login, and the work started on the key, the window and the counter store, which are all engineering questions and all answerable by the person doing the work. The question that should have been first was not engineering: whose logins are we willing to delay, since one of the tenants is a 400-person office behind one address and a key that includes the source address will lock that office out at 09:00 on a Monday, which is a support incident with a product cause. That question had an owner, cost one message to ask, and changed the design from one counter to two — a tight per-account limit and a loose per-source limit — which is a bigger difference than any tuning of the window would have made. The habit that came out of it is to separate the unknowns that measurement can settle from the ones that only a decision can settle, and to send the message about the second kind before building the first kind, because a design built on a silent assumption about people tends to be rebuilt, and the rebuild is where the time actually goes.
