  AND o.payload @> '{"status":"open"}'
  AND jsonb_path_exists(o.payload, '$.lines[*] ? (@.sku == $s)', jsonb_build_object('s', $2));

CREATE INDEX ON orders USING gin ((payload -> 'status'));
CREATE INDEX ON orders ((jsonb_path_query_array(payload, '$.lines[*].sku'))) ;
Reading: `@>` is containment and is the operator a GIN index answers; `jsonb_to_recordset` turns an array into rows so the shape stays in the query instead of in an ORM unwrapper; the expression indexes match the exact expressions written above, which is why the expressions are written once, in one place.
Pitfall: `payload->'lines'->0->>'sku' = $2` — no index, and a document whose first line is not the one being asked about returns the wrong answer with total confidence.
Verification: EXPLAIN shows the GIN or expression index in use with row estimates near the actual count; a test with a two-line document asserts the query finds the second line.

Task: Rename a column on a 200-million-row table with no downtime window and no dual-write rebellion.
SQL:
BEGIN; ALTER TABLE orders ADD COLUMN delivery_eta timestamptz; COMMIT;
BEGIN; ALTER TABLE orders ADD CONSTRAINT chk_eta CHECK (delivery_eta IS NULL OR delivery_eta > created_at) NOT VALID; COMMIT;
ALTER TABLE orders VALIDATE CONSTRAINT chk_eta;
-- deployments: writes to both, reads from old
BEGIN; ALTER TABLE orders RENAME COLUMN ship_eta TO ship_eta_old; COMMIT;
-- deployments: writes to new only, reads from new
BEGIN; ALTER TABLE orders DROP COLUMN ship_eta_old; COMMIT;
Reading: expand, migrate, contract. Every step is a separate transaction so a deploy can be rolled back to the previous shape, and `NOT VALID` then `VALIDATE` splits the cheap lock from the long scan, so the scan happens while nothing is waiting on a lock.
Pitfall: one migration that renames and validates in a single transaction, which holds an access-exclusive lock long enough that the deploy window becomes a queue; and the "temporary" dual-read path that is still in the codebase a year later because the contract step was never scheduled.
Verification: each step replays against a production snapshot; the old and new code versions are exercised against every intermediate schema by the deploy test, and the contract migration exists as a scheduled ticket rather than as a comment.

Task: Serve a hot read-only query from an index-only scan, then explain why it degraded after the table got busy.
SQL:
CREATE INDEX idx_orders_tenant_created ON orders (tenant_id, created_at) INCLUDE (status, total);
EXPLAIN (ANALYZE, BUFFERS)
SELECT status, total FROM orders WHERE tenant_id = $1 AND created_at > now() - interval '7 days';
Reading: an index-only scan answers from the index but must confirm visibility from the visibility map, so a page that has been modified since the last vacuum is fetched from the heap anyway. The plan flips from "Index Only Scan" to "Index Scan" with heap fetches climbing in EXPLAIN BUFFERS, and the shape of the query has not changed at all — only the update pattern has.
Index Only Scan using idx_orders_tenant_created on orders  (cost=0.42..88.4 rows=184) (actual time=0.081..2.11 rows=184 loops=1)
  Index Cond: ((tenant_id = '9b1...'::uuid) AND (created_at > (now() - '7 days'::interval)))
  Heap Fetches: 21433
Buffers: shared hit=1982 read=14412
The query did not change; `Heap Fetches` did. After a tuned autovacuum run on that table range the same plan reports `Heap Fetches: 0` and the `read=` count collapses to hits.

Task: Read a balance and its ledger rows in one request without seeing a half-applied transfer.
SQL:
-- default READ COMMITTED, two statements:
SELECT balance FROM accounts WHERE id = $1;              -- 100
SELECT sum(amount) FROM ledger WHERE account_id = $1;    -- 90, because a transfer committed in between
Reading: under READ COMMITTED each *statement* gets its own snapshot, so the second statement can see a commit the first did not. That is read skew: both numbers are correct and the pair never existed. It is not a bug in the query, and it is not solved by a retry.
Pitfall: summing money in the application from separately consistent reads, then "fixing" it with a `SELECT … FOR UPDATE` that serializes the hot account, or with REPEATABLE READ everywhere, which trades the anomaly for serialization failures that the caller must be able to retry.
Verification: the invariant (balance equals ledger sum) is enforced where it can be — one statement, or a REPEATABLE READ transaction that takes the anomaly as a retryable condition; a test that commits a transfer between the two reads proves the fix holds, with the isolation level named in the test name.

Task: Drain a job table with many workers without making them fight.
SQL:
UPDATE jobs SET status = 'running', worker = $1, started_at = now()
WHERE id = (
  SELECT id FROM jobs WHERE status = 'queued' ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED
)
RETURNING id, payload;
Reading: `SKIP LOCKED` lets each worker take the next unlocked row instead of queueing behind the row another worker holds, which turns a lock convoy into parallel claiming. Doing the claim and the mark in one statement removes the window where two workers both believe they own the row, and `RETURNING` avoids the second round trip.
Pitfall: `SELECT … FOR UPDATE` without `SKIP LOCKED` on a queue, where every worker piles onto the same head row, and the throughput collapses as workers are added; and `NOWAIT` chosen for impatience, which turns contention into errors the caller must handle anyway.
Verification: a test with N concurrent drainers over M rows asserts every row claimed exactly once and no duplicates; the metric that matters is rows per second against worker count, which should be flat-to-rising, not falling.

Task: Normalize emails in exactly one place, in SQL.
SQL:
CREATE OR REPLACE FUNCTION core.normalize_email(p_email text)
RETURNS text LANGUAGE sql IMMUTABLE STRICT PARALLEL SAFE
SET search_path = pg_catalog
AS $$
  SELECT lower(normalize(trim(p_email), NFKC) COLLATE "C")
$$;
SELECT id FROM core.users WHERE email_normalized = core.normalize_email($1);
Reading: the function is the rule behind the generated email_normalized columns, so every lookup and every stored value comes from the same expression. IMMUTABLE plus PARALLEL SAFE keeps it index-friendly, and pinning search_path to pg_catalog closes the search_path hijack that a SECURITY DEFINER-adjacent function would otherwise carry.
Pitfall: trim plus lower in Java, which skips NFKC so a full-width look-alike compares as a different address, and which lowercases non-ASCII that COLLATE C leaves alone, so an address with capital E-acute can never be found.
Verification: a guard test pinning the function text to both generated columns so they cannot drift, plus a fixture with surrounding spaces and full-width characters asserting the same normalized form from SQL and from the repository helper that calls the function.
