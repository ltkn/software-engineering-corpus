Batched and aliased queries also defeat rate limiting keyed on requests per second, because the request count is honest and the work is not.
Attacker outcome: the whole object graph enumerated in one request, including fields no client uses, and either an identity sweep through a field that returns emails or a latency spike bought with a single WAF-visible POST.
Evidence it leaves: one request with an unusual cost profile; a burst of identical resolvers in the trace for a single request id; introspection queried from a user-agent that never queries anything else.
Control: introspection off outside development unless the schema is public by design, query depth and cost limits enforced at the gateway, aliases counted, persisted queries for the known client surface, and field-level authorization asserted by the same test suite that asserts the resolver works.
Detection or regression: a regression probe posts a 200-alias query and a 50-deep query and asserts both are rejected with a documented error rather than a timeout; the schema-diff gate in CI fails on a new field that has no authorization test (contract discipline in 14, mass-assignment shape in 06).

Attack surface: password reset on a legacy front door that builds its email from request headers.
Move: [T1589.001, T1190] header injection in the reset flow — the poison is not XSS, it is the destination of a link the victim is trained to click.

`POST /api/v1/auth/password/reset` with `{"email":"cfo@payments-api.test"}` and `Host: reset.attacker-ops.example` (or `X-Forwarded-Host`, or `X-Forwarded-For`, whichever the template reads)

Why it works: the reset template interpolates whatever it believes is the deployment's own hostname, and behind a proxy the "real" host is a header the client controls, so the link in a legitimate email points at the attacker's host while the token stays valid on the real one. Nobody reviews this path for authorization because it is unauthenticated by design, and nobody rate-limits it well because rate-limiting reset feels cruel.
Attacker outcome: a valid reset token delivered to the attacker for an account the attacker chose, which is account takeover on a path that has no login page to brute force; with `X-Forwarded-For` poisoning, the reset rate limit keyed on that header is bypassed at the same time.
Evidence it leaves: a request with a `Host` value that is not a configured name; an email whose link host differs from the deployment's; a reset for the same address from several header variants in one window.
Control: absolute URLs built from server configuration, not from request headers; the allow-list of accepted forwarding headers declared at the edge and stripped upstream; rate limit keyed on the account and the origin IP together, never on a client-supplied header alone (07 owns the token-binding requirement, 09 owns the header-hygiene side).
Detection or regression: a probe that sends an unknown `Host` and asserts the reset email still contains the configured host, asserted in the pipeline against the real mail sink rather than against a mocked template renderer.

Attack surface: a database the attacker can query as a low-privilege role, plus statistics views that record more than anyone intended.
Move: [T1005, T1552.001] read the observability surface instead of the data. `pg_stat_statements` keeps normalised query text; application logs, `pg_stat_activity`, and `pg_stat_user_tables` keep names, states and access patterns, and any codebase that interpolates a parameter into a query has just written that parameter into a shared view.

`SELECT queries FROM pg_stat_statements LIMIT 20;`

Why it works: the statistics views are granted to almost every role because monitoring needs them and nobody wants to write a grant, so they become a free enumeration of the schema and of how the application actually reaches it. A query text with a literal token, session id or webhook secret in it is a credential store that no secret scanner looks at, because it is not a secret file.
Attacker outcome: the real table and column names before anyone asks a question, the shape of the queries the application writes (which tells the attacker where the string concatenation lives), and occasionally a literal that turns a low-privilege role into a valid session for another tenant.
Evidence it leaves: statistics view reads from a role that has no business reading them, from a host that is not the monitoring service; `pg_stat_statements_reset` never called, so the view holds months of application history.
Control: least privilege applied to the statistics views as seriously as to the tables, literal-free queries enforced by review and by a lint that catches string-built SQL, monitoring given a named role with a narrow grant so an unexpected reader is audible, and the query-text surface treated as a log destination when the parameter might carry a token.
Detection or regression: a test asserts no application query text reaches the statistics views with a quoted literal in a credential position; a database audit rule alerts on statistics-view reads by any role outside the monitoring allow-list (heapdump-side loot in the same estate is the neighbouring record, log-payload discipline is 09's).

Attack surface: a lockfile that is correct, reviewed, and green in `npm audit`.
Move: [T1195.002] the mutation class of supply-chain attack: a version already in the lockfile is republished or a new patch version appears from a maintainer handover, so nothing in the diff looks new. During the 2025 npm worm wave, the compromised package was not exotic, it was a widely depended-on build-time package, and the payload ran in CI with the runner's own credentials, then wrote itself back into the registry as future versions of itself.

`npm ci && node -e "console.log(require('some-build-dep/package.json').version)"` compared against the version the review approved last week

Why it works: install-time scripts execute with the developer's or runner's filesystem and credential read access, and a lockfile pins a version number, not the bytes behind it, so an identical string can mean different code. A version that no maintainer remembers publishing passes every human check, because the check is "is this dependency already ours", and the answer is yes.
Attacker outcome: code execution on every CI runner that installs the package, which means the signing key, the npm token, and the repository's write access; the worm variant then compromises the dependencies of whoever installs the affected version, so the next victim is a build with no new dependency in it at all.
Evidence it leaves: a `package-lock.json` diff that is empty while the installed tarball hash changed; registry provenance for the version pointing at a run nobody recognises; CI logs with an outbound request to a new host during install, and a new npm token created for the publish.
Control: install with scripts disabled by default and an explicit allow-list for the handful of packages that genuinely need them, integrity hashes checked rather than trusted, publish provenance required and verified, dependency updates through a bot that shows the diff a human reads, and CI tokens scoped to the repository with no publish permission unless the job is the publish job (26 kind 4 owns the CI credential scope, 09 the egress allow-list).
Detection or regression: a CI step asserts the resolved tarball hashes match the recorded set for the same version string, and a drill with a fixture package whose install script reads a token proves the allow-list stops it.

Attack surface: a developer shell obtained through a phishing page or a compromised laptop, with no lateral movement needed at all.
Move: [T1552.004, T1552.001, T1555] read the box the way the on-call uses it: the CLIs are already authenticated, and the tokens they hold are scoped to whatever the human can reach.

`cat ~/.aws/credentials ~/.kube/config ~/.config/gh/hosts.yml ~/.docker/config.json; gh auth token; aws sts get-caller-identity; history | grep -E 'psql|kubectl|curl -u'`

Why it works: developer credentials are issued for convenience and rarely expire on a schedule, the CLI config files are world-readable in a home directory, and shell history is a written record of every secret a person has ever typed into a command line, including the ones that were supposed to be one-off. From here the intrusion does not need an exploit: it needs one `kubectl get secrets` on a namespace the human was granted months ago for a migration.
Attacker outcome: a long-lived cloud credential, a kubeconfig with cluster access, a GitHub token that can read private repositories and, on a machine that ran a build, an npm or registry token — which turns a single laptop into the supply chain (the mutating side of that is the neighbouring record).
Evidence it leaves: an identity used from an unusual source address with an unusual user-agent; `aws sts get-caller-identity` style discovery calls in the audit log; a `gh api` sweep of private repositories; secrets read in bulk from a namespace the human never touches during the day.
Control: short-lived credentials through an identity broker instead of long-lived access keys in a dotfile, hardware-bound sessions for anything that can reach production, a policy that CI tokens and human tokens are never the same token, and the standing assumption that a laptop is readable so production reach is a separate, audited grant (cloud-role containment in 09 kind 3, IAM persistence in 31's own RBAC records).
Detection or regression: an alert when a human identity calls production-only APIs outside a session issued through the broker; a drill where a fake laptop credential performs a repository sweep and a bulk secret read, and both page with the identity named.
