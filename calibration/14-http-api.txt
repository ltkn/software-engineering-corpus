Design decision: retries get a budget and hedging is a policy, both expressed per endpoint rather than per call site.
Contract fragment:
{ "endpoint": "GET /stock/{sku}",
  "timeoutMs": 120, "maxAttempts": 3, "backoffMs": [30, 90], "jitter": true,
  "retryOn": ["connect-error", "429", "503"], "budgetRatio": 0.10,
  "hedge": { "enabled": true, "percentile": 0.75, "maxInFlight": 2 } }
Why: retries that ignore each other are how a small dependency error becomes a self-inflicted storm, so the budget — retries as a fraction of total requests — caps the amplification, and only idempotent, timeout-or-overload conditions are retryable. Hedging a read at the p75 latency is cheaper than a longer timeout for the tail, but only for reads that are cheap to duplicate; hedging a write is a duplicate-side-effect design decision, not a tuning knob.
Versioning note: budgets belong to the client's contract with itself, so they change without a version bump — but the `Retry-After` semantics the server sends are contract and must not be silently ignored by a client that has its own cadence.
Verification: a fault-injection test with the dependency at 30% failure asserts the retry ratio stays inside the budget and the additional load is what the model predicts; a test with a slow p99 asserts hedged reads return at about p75 without exceeding `maxInFlight` (the pattern's architectural framing is 19, the failure transcripts are 02).
