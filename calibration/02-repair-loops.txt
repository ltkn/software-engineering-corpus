(4) Log files on the container filesystem — ruled out, ephemeral storage flat. (5) `smaps_rollup` versus heap showed 300Mi of anonymous memory outside the heap, the number that split the problem in two. (6) `jcmd 1 VM.native_memory summary` with NMT on attributed most of it to native (Internal plus Other): direct buffers from a Netty client, plus per-thread arenas. (7) The arenas were glibc's — 200 worker threads, default arena count, several hundred Mi of fragmentation that grows with the import's thread count and never comes back. (8) The question nobody asked until step 7: is the container limit a measured need or a number copied from another service? It was copied.
Fix: `MALLOC_ARENA_MAX=2`, direct-buffer memory bounded explicitly and included in the limit calculation, thread count sized to the pool it serves, limits recomputed from the working set plus stated headroom, and the eviction alert wired to the working-set ratio rather than to the node condition.
Verify:
Working set peaks at 380Mi under the same import, zero evictions across a fortnight of nights, and a test asserts heap plus max direct buffers plus thread stacks fits under the container limit with the numbers written out.

Failure:
A 400ms p99 tail on the reporting read path every night between 02:00 and 03:30, no errors, and the application's own dashboards look normal.
Diagnosis: Seven steps and one wasted afternoon. (1) The batch import — real, but the trigger rather than the cause, because the same import ran a month ago without the tail. (2) Lock contention — ruled out: `pg_stat_activity` showed tuple-lock waits for a handful of queries, nowhere near the tail's frequency. (3) Autovacuum not running — ruled out by the logs, it ran constantly. (4) The index being skipped — the wasted afternoon: an index was added, the tail did not move, and `EXPLAIN` later showed it was never chosen because the query filters on a `created_at` range and the new index led with `tenant_id`. (5) The number that ended the guessing: `Heap Fetches: 21433` in an otherwise clean index-only scan, and `pg_stat_user_tables.n_dead_tup` for that table range had grown fortyfold since the import started writing and deleting. (6) Autovacuum was running and losing: the default scale factor for a table that size fires far too late, and its cost limit throttled it into irrelevance against the import's write rate. (7) The scope question that mattered: is the import allowed to run in the primary's window at all, or is that an accident of history? Answer: accident.
Fix: Per-table `autovacuum_vacuum_scale_factor=0.02` with a raised cost limit on that table, the import moved to its own window with a batch size bounded by the write-rate budget, and the covering index dropped — it cost writes and bought nothing.
Verify:
`Heap Fetches` near zero during the nightly window, p99 flat at 61ms through the import, and a monitoring assertion on dead-tuple ratio per hot table so the next occurrence is a page about a number rather than a hunt through plans.
