Goal: Query key factories as the single source of cache identity.
Wiring:
export const userKeys = {
  all: ["users"] as const,
  list: (tenant: string, cursor: string | null, limit: number) =>
    [...userKeys.all, tenant, cursor, limit] as const,
};
Why: factories make keys structural and greppable; inline literals diverge across components and invalidations miss half the views.
Pitfall: ["users", tenantId] in one component and ["users", tenant] in another — same data, two caches, stale forever.
Verification: key-equality test (same inputs, identical keys); key-literal lint bans inline arrays outside factories.

Goal: Query functions with AbortSignal plumbed end to end.
Wiring:
queryFn: ({ pageParam, signal }) => fetchUsers(tenant, pageParam ?? null, 25, signal),
Why: cancellation on unmount and refetch races prevents stale writes from slow responses arriving late.
Pitfall: fetch without signal — unmounted component state updates plus wasted bandwidth on every keystroke search.
Verification: unmount-mid-fetch test asserts abortion; race fixture (slow-then-fast) resolves to latest only.

Goal: Stale and GC time selection per data volatility.
Wiring: staleTime 30s with gcTime 5min for user lists; staleTime 0 for checkout totals; gcTime longer than the longest reasonable background return.
Why: staleTime decides refetch-on-mount behavior; gcTime decides cache survival; reference data and transactional data want opposite settings.
Pitfall: defaults everywhere — checkout totals served stale for minutes, reference lists refetched per navigation.
Verification: volatility matrix per query (stale/GC values with rationale); staleness test asserts refetch behavior per class.

Goal: Structural sharing awareness for render performance.
Wiring: rely on v5 structural sharing default (unchanged data keeps referential stability); select() to subscribe components to slices.
Why: stable references skip re-renders; select narrows subscriptions so list rows do not rerender on unrelated cache updates.
Pitfall: spreading query data into new objects per render, defeating sharing and rerendering everything always.
Verification: render-count test on scroll/update scenarios; select-slice test asserts isolated rerenders.

Goal: Mutation lifecycle with rollback context.
Wiring:
useMutation({
  mutationFn: updateUser,
  onMutate: async (next) => { await queryClient.cancelQueries({ queryKey: userKeys.list(...) }); const prev = snapshot(); applyOptimistic(next); return { prev }; },
  onError: (_e, _v, ctx) => restore(ctx.prev),
  onSettled: () => invalidate(),
});
Why: cancel-then-snapshot-then-apply makes optimism safe; error path restores exact prior state; settled invalidation reconciles with the server.
Pitfall: optimistic apply without snapshot — failed mutations leave invented data in the cache permanently.
Verification: failure-injection test asserts cache equals pre-mutation state; settled-invalidation asserted via network log.

---

Goal: Retry policy per mutation kind, never global.
Wiring: idempotent updates retried twice with backoff; payments and charges never retried automatically (manual retry with idempotency key instead).
Why: retrying a charge duplicates money; never retrying a profile update fails users on transient blips.
Pitfall: global retry 3 on the mutation defaults — safe for reads-shaped writes, catastrophic for charges.
Verification: retry-policy matrix per mutation; charge-mutation test asserts single execution under fault injection.

---

Goal: Cancellation coordination between mutations and in-flight queries.
Wiring: cancel affected queries in onMutate, restore-then-invalidate in onError/onSettled, single-flight on the manual retry button.
Why: overlapping mutation and refetch interleave into lost updates or duplicated effects.
Pitfall: retry button spammable during flight, stacking three identical mutations.
Verification: double-click drill asserts single effect; in-flight overlap test asserts serialized outcomes.

Wiring:
useInfiniteQuery({

Goal: Port a v4 store to vue-query v5 without silent behavior changes.
Why: Every rename is a breaking change that the compiler does not flag: cacheTime is gcTime, isLoading collapsed into isPending (isLoading now means pending-and-fetching), status "loading" became "pending", keepPreviousData was replaced by placeholderData, onSuccess/onError/onSettled were removed from useQuery (they stay on mutations), useErrorBoundary became throwOnError, and every call site moved to the object-only signature.
legacy/counter form:
useQuery(['users', tenant], fetchUsers, { cacheTime: 5 * 60 * 1000, onSuccess: (d) => keys.set(d) })
fix:
useQuery({ queryKey: ['users', tenant], queryFn: fetchUsers, gcTime: 5 * 60 * 1000, placeholderData: keepPreviousData })
misconfiguration: Reading loading as "pending" sends the loader UI at a completed query on the next focus refetch; switching to status === 'pending' fixes it.
verification: Type-check fails on every old call site before the first runtime test, which is the point of the object-only signature — the compiler now catches the rename.

Goal: Keep server state out of Pinia and in Query keys instead.
Why: The moment a query result is copied into a Pinia store, invalidation has to be reimplemented by hand; queryOptions lets the same typed key, queryFn, staleTime, and gcTime travel from the route loader to the hook without drift. Optimistic mutation is then keyed to the same tuple, so the optimistic row and the query result reconcile on invalidation instead of negotiating.
snippet:
export const usersOptions = (tenant: string) => queryOptions({
  queryKey: ['users', tenant] as const,
  queryFn: ({ signal }) => fetchUsers(tenant, signal),
  staleTime: 30_000, gcTime: 5 * 60_000,
});
mutation:
const m = useMutation({
  mutationFn: (input: NewUser) => postUser(input),
  onMutate: async (input) => {
    await queryClient.cancelQueries({ queryKey: ['users', tenant] });
    const prev = queryClient.getQueryData(['users', tenant]);
    queryClient.setQueryData(['users', tenant], (old) => [...old, { ...input, id: 'optimistic' }]);
    return { prev };
  },
  onError: (_e, _i, ctx) => queryClient.setQueryData(['users', tenant], ctx.prev),
  onSettled: () => queryClient.invalidateQueries({ queryKey: ['users', tenant] }),
});
misconfiguration: optimistic rows keyed to a different tuple survive the invalidation and linger as phantom rows.
verification: A mutation test with a mocked 409 asserts the optimistic row is rolled back, the prev cache payload is restored, and a simultaneous background-refresh returns one page, not a duplicate.
