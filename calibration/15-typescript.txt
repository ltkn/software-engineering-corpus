Goal: Make route and event strings checked rather than remembered, without losing inference at the call sites.
Wiring:
type Route = `/orders/${string}` | `/orders/${string}/lines/${string}` | "/healthz";
type Parse<S extends Route> = S extends `/orders/${infer Id}/lines/${infer Line}`
    ? { kind: "line"; orderId: Id; lineId: Line }
    : S extends `/orders/${infer Id}` ? { kind: "order"; orderId: Id } : { kind: "root" };

const r = route("/orders/ord_41/lines/ln_7");     // { kind: "line"; orderId: "ord_41"; lineId: "ln_7" }

Counter-form: a `Record<string, Handler>` map plus a runtime regex, where a typo is a 404 in staging rather than an error at compile time.
Verification: a type-level assertion test asserts `Parse<"/orders/a/lines/b">` is the line shape and that `route("/orders/")` errors; it runs in CI next to `tsc7 --noEmit`, so the assertions are enforced rather than decorative.

`src/api/routes.ts:41:18 - error TS2345: Argument of type '"/orders/"' is not assignable to parameter of type 'Route'.` — the trailing slash is the whole message, and it arrives at compile time in the file that owns it.

Goal: Keep a callback-heavy public API's variance honest instead of discovered by a downstream build.
Wiring:
interface Handler<in T> { handle(event: T): void }
interface Source<out T> { read(): T }
declare function pipe<A, out B>(s: Source<A>, h: Handler<in A>, map: (a: A) => B): Source<B>;
Why: variance annotations state the intended subtyping and make the compiler enforce it, so a `Handler<SuperEvent>` is assignable where `Handler<SubEvent>` is expected for the right reason and a wrongly-varied parameter is an error at the declaration rather than in a consumer's build three repos away. Function parameters are contravariant and results covariant whether or not the annotation is written; writing it down is what stops a refactor flipping it unnoticed.
Why it stays: the annotation is checked, so `out T` on a type that also writes `T` fails to compile instead of lying.
Counter-form: `any` in a callback position, which is bivariant enough to accept everything and therefore catches nothing; or a generic parameter that appears only in parameter position but is annotated `out` because it read like a result.
Verification: the published package's declaration files are compiled by a fixture consumer project on both compilers, and the build fails if a widening assignment that should be an error is accepted.

Goal: Give a config object a type that is both checked and readable when someone gets it wrong.
Wiring:
type Depth = [never, 0, 1, 2, 3];
type Validated<T, D extends 0 | 1 | 2 | 3 = 3> =
    D extends 0 ? { error: "recursion-too-deep" }
  : T extends readonly unknown[] ? { [K in keyof T]: Validated<T[K], Depth[D]> }
  : T extends object ? { [K in keyof T]: Validated<T[K], Depth[D]> }
  : T;
interface FeatureFlags extends Validated<typeof flagsSchema> {}
const flags = { payments: { retries: { enabled: true, max: 3 } } } satisfies Validated<typeof flagsSchema>;
Why: the depth parameter keeps a recursive mapped type from exhausting the instantiation depth, which is the difference between a type that models the shape and a type that makes the compiler time out and report something unrelated. `satisfies` keeps the literal inference (so `max` stays `3`, not `number`) while still checking the shape — an annotation would erase exactly the precision that makes the flags usable downstream.
Why it stays: error text names the offending key because the mapped type mirrors the shape, so a mistake reads as `payments.retries.max` rather than as a wall of unresolved generics.
Counter-form: a JSON-schema-in-a-generic stack that is technically complete and unmaintainable, or `as const` everywhere, which checks nothing.
Verification: a type test asserts the literal types survive (`Expect<Equal<typeof flags.payments.retries.max, 3>>`) and that a wrong leaf type produces an error mentioning its path.

Wiring:
