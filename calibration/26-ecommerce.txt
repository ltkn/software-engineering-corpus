Goal: Catalog modeling separating sellable truth from channel presentation.
Pattern: PIM holding canonical product plus variants (size/color with distinct SKUs), channel-specific titles/images/prices as overlays, never forks.
Why: one truth with overlays serves web, mobile, and marketplace consistently; forked catalogs diverge within a quarter.
Pitfall: per-channel product tables with "temporary" sync jobs reconciling them nightly.
Verification: overlay-coverage test (every channel renders from canonical plus its overlay); fork-detection audit (duplicate SKUs across tables fail the build).

Goal: Variant and SKU discipline that survives scale.
Pattern: variant axes declared per product family (size, color), SKU per purchasable combination, optionality explicit; bundles as containers referencing SKUs, never pseudo-SKUs with hidden contents.
Why: inventory, pricing, and fulfillment all key on SKU; ambiguous granularity corrupts every downstream number.
Pitfall: "one size" pseudo-SKU hiding three physical variants, inventory permanently wrong.
Verification: SKU-uniqueness plus variant-completeness tests; bundle-explosion test (contents resolve deterministically).

Goal: Pricing engine with rule precedence and auditability.
Pattern: base price, then stacked adjustments in fixed precedence (sale, coupon, loyalty, volume) each recorded as line items; effective-price function pure and replayable.
Why: precedence disputes ("which discount applied?") resolve from the recorded stack; replayability makes support and testing deterministic.
Pitfall: final-price floats stored without the adjustment trail, disputes unresolvable.
Verification: price-replay test (same inputs, same itemization); precedence-conflict fixture resolves per the documented order.

Goal: Promotions as versioned rules with guardrails, not code deploys.
Pattern: promotion definitions (eligibility, benefit, caps, windows) as data with start/end, budget caps, per-account limits, and kill switches; engine evaluates deterministically.
Why: marketing moves at campaign speed; code deploys for "weekend 20% off" couple revenue to release trains.

Verification: abuse-loop drill (profitable repetition capped by design); expired-promotion test (outside window, no discount).

Goal: Cart as a priced snapshot with explicit expiry, not live queries.
Pattern: cart lines snapshot price and availability at add-time with a validity window; revalidation on checkout start; abandoned-cart retention per policy.
Why: price changes mid-checkout create disputes; snapshots make the checkout price a promise with a deadline.
Pitfall: live-price-at-payment charging a different total than displayed, with support tickets as the reconciliation system.
Verification: price-change-during-checkout drill charges the snapshotted total or re-consents explicitly; expiry test revalidates past the window.

---

Goal: Checkout as an explicit state machine, not a script.
Pattern: states (cart, details, payment_pending, authorized, captured, fulfilled, refunded, failed) with allowed transitions enumerated; every transition an event with idempotency.
Why: implicit checkout flows strand orders in undefined states ("paid but not created"); enumerated transitions make orphans impossible by construction.
Pitfall: boolean flags (paid=true, shipped=false) combining into twelve undocumented states.
Verification: state-coverage test (every state reachable in tests, every transition exercised); orphan-state probe (no order outside the machine) nightly.

Goal: Inventory reservation with oversell prevention at scale.
Pattern: reserve on checkout start with TTL (minutes), confirm on capture, release on expiry/failure; stock decremented at reservation, not at payment.
Why: selling the last unit twice is the cardinal ecommerce sin; reservation serializes contention at the decision point.
Pitfall: check-then-decrement races under flash-sale concurrency, overselling 300 units of 100.
Verification: concurrency drill (10x buyers, 100 units) sells exactly 100 with fair failure for the rest; expired reservations release provably.

Goal: PaymentIntent lifecycle on current Stripe API (dahlia line, 2026-08-26 current; monthly backward-compatible upgrades, majors versioned).
Pattern: one PaymentIntent per order/session; create with amount/currency plus automatic payment methods; handle requires_action (3DS) via the SCA engine default of automatic; capture on fulfillment (manual capture for delayed shipment); reuse the same intent across retries.
Why: the intent object is the payment's state machine mirroring the order's; automatic 3DS delegates SCA decisions to risk data instead of static rules.
Pitfall: new intent per retry attempt, orphaning authorizations that later capture unexpectedly.
Verification: retry drill reuses the intent; status-transition test covers requires_action/succeeded/failed/canceled paths.

Goal: 3DS/SCA handling with exemption strategy, not blanket friction.
Pattern: automatic 3DS (SCA engine decides per risk), request_three_d_secure any only from fraud-engine logic; frictionless preference where conversion matters; exemption flags where regulation allows low-risk skipping.
Why: every challenge drops conversion measurably; authentication applied by risk, not by fear.
Pitfall: forcing 3DS on all transactions "for security", converting 15% fewer checkouts.
Verification: challenge-rate vs fraud-rate tradeoff reviewed per quarter; exemption-eligible traffic identified and measured.

Goal: Stripe webhooks as the fulfillment trigger, never the client callback.
Pattern: endpoint pinned to an explicit API version, signature verified on raw bytes with the endpoint secret, idempotency on event id, payment_intent.succeeded driving fulfillment; thin vs snapshot payload choice documented per handler.
Why: clients abandon pages post-payment; only webhooks reliably observe completion; version pinning prevents shape drift breaking handlers silently.

Verification: five-case delivery battery (unsigned, wrong version, replay, tamper, out-of-order); closed-tab drill still fulfills exactly once.
